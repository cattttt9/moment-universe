# 技术决策

## 决策：使用共享 UniverseStage

### 背景

首版只在结果页加载 WebGL，前几个阶段使用各自的 Canvas/CSS 背景，切换时空间会中断。

### 选择

在应用根部常驻一个 `UniverseStage`，页面阶段只更新镜头目标、透明度、参数和生成蓝图。

### 原因

- 只保留一个 renderer 和一个 RAF
- 页面切换不会重置星点或出现背景闪烁
- 输入、参数和生成转场可以共享同一空间

### 影响

Three.js 成为首屏资源；通过质量分级、缓存分块和减少动态控制成本。

## 决策：从单模板改为八种原型

### 背景

首版所有结果都使用同一旋臂公式，色板也集中在橙褐色，参数差异无法改变整体轮廓。

### 选择

由稳定哈希先选择原型，再生成统一 `UniverseVisualProfile`，最后由各原型构建粒子。

### 原因

- 结构差异在第一眼可见
- 仍保持相同输入可复现
- 每个原型可以独立测试和维护

### 影响

新增原型必须遵守统一粒子数据合同，海报和 WebGL 仍消费同一蓝图。

## 决策：参数同时影响连续值与结构

### 背景

把三个参数都映射为旋转速度会让交互缺乏意义；每次拖动重建几何又会导致卡顿。

### 选择

拖动期间实时更新速度、发光、对称、湍流、脉冲和尺度；种子或最终配置变化时才重建原型。

### 原因

- 拖动反馈即时
- 避免 pointermove 期间分配大量 BufferGeometry
- 参数映射保持可解释、可测试

### 影响

参数页预览强调连续变化，最终提交后的蓝图再体现结构变化。

## 决策：使用多层粒子形成空间

### 背景

单层粒子与固定镜头缺乏速度差和深度参照。

### 选择

远景星空、中景星尘、前景虚焦粒子使用不同数量、尺寸、速度、视差与透明度。

### 原因

- 不依赖外部图片或视频
- 鼠标与触摸可以产生真实空间反馈
- 各层可按质量等级独立裁减

### 影响

需要统一生命周期和明确释放三个层级的 geometry、material 与 texture。

## 决策：只使用克制的质量分级后处理

### 背景

无 Bloom 时星核和微弱粒子缺乏层次；复杂色差和故障效果又违背安静的视觉方向。

### 选择

high/medium 使用低强度 UnrealBloomPass、ACES 与雾；low 直接渲染并关闭 Bloom。

### 原因

- 增强亮暗关系而不改变暖灰金视觉语言
- 避免多通道色差、重度模糊和高显存链路

### 影响

持续低帧率时会自动关闭后处理并降低像素比。

## 决策：移动端优先保留结构和交互

### 背景

移动 GPU 的填充率、像素比和热限制差异大。

### 选择

减少远中前景粒子、关闭 Bloom、限制 DPR、减少雾层，并在两个四秒窗口低于 42 FPS 后降档。

### 原因

- 主体轮廓和触摸反馈比雾化细节更重要
- 降档不需要重建应用状态

### 影响

真实 iOS/Android 硬件的长时间热稳定性仍需发布前复验。

## 决策：使用纯前端架构

### 背景

作品需要接收用户私密表达，并可直接发布到静态托管。

### 选择

使用 Vite 构建 React 单页应用，所有生成、存储和导出均在浏览器内完成。

### 原因

- 不需要账号、数据库或服务端运维
- 用户文字默认不离开设备
- 可以部署到 GitHub Pages

### 影响

跨设备同步和在线社区不在首版范围内。

## 决策：使用 Three.js

### 背景

星云需要数千粒子、镜头缩放和连续指针交互。

### 选择

Three.js 管理 WebGL 场景，以 `Points`、`BufferGeometry` 和轻量着色器渲染。

### 原因

- 能可靠处理 GPU 粒子和资源生命周期
- 社区成熟，浏览器兼容路径清晰
- 不需要引入复杂游戏引擎

### 影响

必须显式释放几何体、材质、纹理和渲染器，并提供 WebGL 不可用说明。

## 决策：第一版不接入 AI 情绪分析

### 背景

项目根据一句话生成视觉结果，但不应对表达作心理判断。

### 选择

只使用文字哈希和用户自主参数生成宇宙。

### 原因

- 不需要后端或密钥
- 保护隐私且不制造诊断暗示
- 结果可稳定复现

### 影响

宇宙类型描述参数与形态，不代表对用户情绪的判断。

## 决策：采用确定性随机算法

### 背景

相同文字和状态需要产生相同或高度一致的结果。

### 选择

统一哈希文字与参数，使用固定种子 PRNG 生成结构数据。

### 原因

- 可复现、可测试、便于恢复
- 视觉随机逻辑集中，不依赖 `Math.random()`

### 影响

运行时脉冲会随时间变化，但初始结构和类型保持稳定。

## 决策：使用 Canvas 导出海报

### 背景

海报需要合并 WebGL 画面、中文文字和档案信息。

### 选择

先捕获 WebGL Canvas，再在高分辨率 Canvas 2D 上完成排版并导出 PNG。

### 原因

- 浏览器原生、无需后端
- 可以精确排除操作界面
- 支持高分辨率和移动端下载

### 影响

需要处理字体就绪、超长文字换行、Canvas 尺寸和导出异常。

## 决策：移动端采用自适应质量等级

### 背景

移动 GPU、像素比和热限制差异显著。

### 选择

根据触摸能力、视口、设备像素比和减少动态偏好选择高、中、低三档。

### 原因

- 粒子数和像素比是最直接的性能杠杆
- 避免复杂后处理，降低内存和发热

### 影响

低档保留主要星核与交互，但减少粒子、雾化与轨道细节。

## 决策：不使用 Sites 通用项目初始化器

### 背景

项目工作流检测到网站构建能力，但通用初始化器会建立 Vinext/托管结构。

### 选择

遵循用户明确要求，手工建立 Vite React TypeScript 纯静态项目。

### 原因

- 用户明确禁止 Next.js 和服务端
- GitHub Pages 是目标托管方式

### 影响

本项目不会创建 `.openai/hosting.json`，也不会自动发布到其他托管平台。

## 决策：延迟加载 WebGL，不引入后处理链

### 背景

同步引入 Three.js 后，首个生产构建的单体 JavaScript 约 789 kB；Bloom 等后处理还会增加
移动端显存、包体和资源释放复杂度。

### 选择

结果阶段通过 `React.lazy` 加载 `UniverseCanvas`，使用柔边点精灵和雾化 Sprite 代替 Bloom。

### 原因

- 欢迎、输入和参数阶段不需要下载 WebGL 模块
- 保持单一 renderer 与明确的释放边界
- 低性能设备也能保留核心视觉

### 影响

首次进入结果页会短暂显示“正在点亮星核”，最终构建拆为约 295 kB 主包与 494 kB WebGL 包。
