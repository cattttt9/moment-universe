# 《此刻宇宙》技术总结

## 1. 项目背景

《此刻宇宙》把用户主动留下的一句话与能量、秩序、波动三个参数转化为数字艺术作品。
关键约束不是“智能分析”，而是纯本地、可复现、可互动和可保存。用户表达不应被上传，
也不应被包装成情绪诊断。

## 2. 最初需求

MVP 覆盖六段体验：欢迎、文字输入、状态校准、文字粒子转场、动态星云和宇宙档案。
工程层面还要求 GitHub Pages、ZIP 分发、移动端降级、无障碍、完整文档和清晰 Git 历史。

## 3. 最终技术架构

```text
React 应用状态
├─ 输入与轨道参数组件
├─ 确定性引擎
│  ├─ UTF-8 文本哈希
│  ├─ 固定种子随机数
│  └─ UniverseBlueprint
├─ 两条视觉输出
│  ├─ Canvas 2D 文字粒子转场
│  └─ Three.js WebGL 星云
└─ 两条持久输出
   ├─ localStorage 最近档案
   └─ Canvas 2D PNG 海报
```

React 只保存阶段、原句、参数、当前配置和少量 UI 状态。粒子蓝图由 `useMemo` 根据
配置和质量等级生成；Three.js 场景在结果阶段动态加载，不进入首屏主包。

## 4. 核心数据流

1. 输入被 NFC 规范化、去除首尾空白并限制为 80 字。
2. 规范化文字与三个整数参数拼接后执行 UTF-8 FNV-1a 哈希。
3. 哈希种子驱动固定 PRNG，生成类型、色板、旋臂数、星核数和粒子属性。
4. 同一 `UniverseConfig` 同时服务 WebGL、海报和 localStorage，避免三套规则漂移。
5. `createdAt` 参与档案时间和编号，不参与核心几何种子，因此不会破坏结构复现。

## 5. 粒子系统实现

`universeGenerator.ts` 预先计算粒子的基础位置、尺寸、相位、分支和亮度。位置使用旋臂角、
半径分布、秩序系数和波动扰动组合。WebGL 端只上传紧凑的 Float32 BufferAttribute。

顶点着色器负责连续旋转、纵向波动、脉冲缩放和指针局部位移；片元着色器绘制柔边圆点，
使用加色混合。这样每帧不需要在 JavaScript 中遍历几千粒子。

## 6. 文字转粒子的实现

文本先按字符宽度换行并绘制到离屏 Canvas，随后每 6–7 像素读取一次 alpha。
有效像素最多采样 1600 个，手机最多 900 个。每个样本生成稳定的漂移与星云目标位置。

GSAP 只推进一个 0–1 的进度值；Canvas 根据进度计算原位、碎裂、中心坍缩和旋臂成形。
该方案不解析字体轮廓，中文系统字体可直接使用，复杂度也明显低于 TextGeometry。

## 7. 确定性随机算法

哈希层使用 FNV-1a，输入先通过 `TextEncoder` 转 UTF-8，避免直接遍历 UTF-16 造成中英文
行为差异。PRNG 使用 xmur3 派生状态与 Mulberry32 风格步进。所有结构随机都通过
`createSeededRandom` 或带粒子索引的子种子产生，生产代码不依赖 `Math.random()`。

测试验证了文本哈希、序列复现、参数限制、宇宙类型和粒子蓝图前五项的一致性。

## 8. Three.js 资源管理

场景仅由 `UniverseCanvas` 创建一个 RAF。`visibilitychange` 在页面隐藏时取消循环，恢复时
重置时间基准。组件卸载按顺序清理交互监听器、几何体、材质、CanvasTexture、场景、
renderer 和 WebGL context，并移除 renderer Canvas。

星云模块通过 `React.lazy` 加载。最终构建约为 295 kB 主包与 494 kB WebGL 包，避免首屏
加载原先约 789 kB 的单体 JavaScript。

## 9. 动画时间线设计

完整生成时间线为 4.2 秒：

- 0–12%：原句保持可辨识；
- 12–38%：像素产生轻微漂移；
- 36–64%：粒子坍缩到中心；
- 69–100%：粒子展开为扁平旋臂；
- 结束后延迟 180 ms 进入 WebGL 结果。

减少动态路径缩短到 0.55 秒，CSS 同时关闭几乎所有长动画。用户可以随时跳过。

## 10. Canvas 海报导出

海报尺寸固定为 1800×2400。先捕获 renderer Canvas，再裁切到 1620×1120 的视觉窗口，
叠加上下渐隐；随后绘制项目名、自动换行原句、日期、编号、类型和参数。

当 WebGL 捕获为空或图片解码失败时，直接以 `UniverseBlueprint` 在 Canvas 2D 中绘制
确定性粒子，因此 WebGL 降级不会连带破坏海报。`toBlob` 返回空值时会向用户展示可重试
错误，不会静默失败。

## 11. 移动端性能优化

质量等级综合视口、粗指针、设备像素比、可用 `deviceMemory` 和减少动态偏好：

| 等级   | 最大基础粒子 | 像素比上限 | 雾化 Sprite |
| ------ | -----------: | ---------: | ----------: |
| high   |         7200 |        1.8 |           5 |
| medium |         4300 |        1.4 |           3 |
| low    |         2200 |        1.0 |           1 |

手机竖屏采用低档，轨道减少为一条；交互仍保留。`100dvh`/`100svh` 与 safe-area inset
避免地址栏和刘海区域破坏布局。

## 12. 遇到的真实问题

1. 初始目录为空且不是 Git 仓库。
2. 通用站点初始化器会引入与需求冲突的 Vinext 结构。
3. 首次测试在沙箱内启动 esbuild 时遇到 `spawn EPERM`。
4. CSS Modules 缺少 Vite 类型声明，TypeScript 无法识别 `.module.css`。
5. localStorage 记录的 `version: 1` 被推断为普通 `number`。
6. Three.js 与 GSAP 初次进入同一主包，产生约 789 kB JavaScript。
7. Archiver 8 已移除默认导出，旧示例写法运行时报错。
8. 内置浏览器成功执行 PNG 逻辑，但没有向验收 API 暴露 download event。

## 13. 问题定位过程

- 先运行独立的 lint、test、typecheck、build，区分代码错误与运行环境权限。
- 对 TypeScript 错误只添加最小声明和字面量约束，再重新构建。
- 读取 Vite gzip 报告确认大包来自同步 Three.js 依赖。
- 检查 `node_modules/archiver/package.json` 与实际导出键，确认版本 8 改为具名类。
- 浏览器验收同时查看 DOM 快照、截图和 console warn/error，区分工具遥测错误与页面错误。

## 14. 采用的解决方案

- 权限问题按环境要求允许 npm/esbuild 子进程，不修改系统配置。
- 增加 `src/vite-env.d.ts` 与 `as const`，不降低 TypeScript 严格度。
- 使用 `React.lazy` 动态加载整个 WebGL 模块。
- ZIP 脚本改用 `new ZipArchive()`，实际生成并记录 1.06 MiB 产物。
- 下载验证以页面成功状态为依据，同时把真实设备落盘复验留在 P1。

## 15. 放弃过的方案及原因

- **Vinext/通用托管初始化**：与 Vite、GitHub Pages 和禁止服务端的明确要求冲突。
- **字体轮廓 TextGeometry**：中文字体加载、授权、体积与三角面数量风险过高。
- **复杂 Bloom 后处理**：会增加移动端显存和渲染链路，柔边粒子与 Sprite 已满足视觉目标。
- **把原句写入分享 URL**：存在隐私泄露风险；首版优先图片分享。
- **实时 CPU 更新每个粒子**：主线程成本随粒子数线性增长，改由 shader 处理。

## 16. AI 辅助开发中有效的做法

- 先把验收命令、目录和文档台账建立，再逐阶段实现。
- 每个功能完成后立即构建并创建独立提交，错误更容易定位。
- 用浏览器真实走流程，而不只根据源码推断视觉完成。
- 把复杂“随机”统一收口到引擎，测试无需理解 React 或 Three.js。

## 17. AI 生成代码需要人工检查的地方

- WebGL 对象是否每一个都有对应 `dispose`。
- React StrictMode 下是否出现重复 RAF 或监听器。
- 触摸双击与双指缩放是否和页面滚动冲突。
- Canvas 中文字体、超长换行和 iOS 下载行为。
- GitHub Pages 子路径和自定义域名 base 是否匹配。

## 18. 本项目中获得的技术提升

- 将确定性生成数据与实时 shader 动画分离，既可复现又保持生命感。
- 用同一蓝图支撑 WebGL、降级 Canvas、海报与历史恢复。
- 对首屏做模块级延迟加载，而不是只压缩资源。
- 以可见 DOM、截图、控制台和构建报告组合验证互动艺术网页。

## 19. 当前不足

- 尚未在真实 iPhone Safari 与 Android Chrome 硬件上验收手势和文件落盘。
- 质量等级只有自动选择，没有用户手动覆盖和实时帧率下调。
- 首版只有 3:4 海报。
- 分享参数解析已测试，但产品界面没有开放分享链接，避免不完整复现。
- 没有自动视觉回归测试。

## 20. 后续优化方向

优先完成真实移动设备矩阵、帧率采样降档和海报多比例；随后可增加应用内清空确认、
更明确的首次手势引导和不暴露原句的完整视觉复现链接。
